01Executive Summary & Project Scope

Project overview, objectives, and scope definition.

Problem Statement

Traditional cybersecurity education relies heavily on theoretical knowledge delivery — lectures, slides, and static documentation. While these methods build foundational awareness, they fail to develop the practical investigative instinct required for real-world security assessment. Students struggle to connect abstract vulnerability concepts (OWASP Top 10, CWE classifications) to concrete exploitation patterns they would encounter in professional environments.

Furthermore, existing hands-on platforms (Hack The Box, TryHackMe, DVWA) require complex server setup, introduce real attack surface risks, and often overwhelm beginners with minimal guided methodology.

Proposed Solution

Cyber Labs is a purpose-built, interactive cybersecurity learning platform that bridges this gap. It provides five structured vulnerability investigation labs running entirely within the browser — requiring zero server setup, zero external network access, and zero risk of unintended system compromise. Each lab follows a guided Observe → Probe → Decide → Mitigate methodology designed to build cumulative defender instinct.

✅ Key Differentiator Unlike traditional CTF platforms, Cyber Labs operates 100% client-side with scripted simulations. This eliminates deployment complexity, removes all external risk surfaces, and enables instant accessibility for 500+ concurrent users via edge-deployed static hosting — without any backend infrastructure.

Project Objectives

  • Build a Safe Simulation Environment — 100% client-side cyber range simulating real vulnerabilities (authentication bypass, IDOR, XSS, security misconfiguration, HTTP header analysis) with zero external dependencies.
  • Design Progressive Learning Paths — Sequential multi-step investigations that build cumulative expertise across five distinct vulnerability domains.
  • Implement Adaptive Scoring — Standardized base-100 scoring with attempt-based deductions, hint penalties, and deterministic achievement mechanics.
  • Deliver Production-Grade Quality — Responsive design, accessibility compliance, sub-120KB bundle, optimized Lighthouse scores, and zero build errors.
  • Enable Scalable Deployment — Edge-deployed on Vercel CDN with GitHub-integrated CI/CD for automatic, zero-downtime deployments.

Scope Boundaries

✅ In Scope

  • 5 interactive security investigation labs
  • 4 purpose-built simulation engines
  • Adaptive scoring & achievement system
  • Dashboard with skill radar analytics
  • Sequential lab locking & retake system
  • Responsive UI (390px → 4K)
  • Production deployment & CI/CD pipeline

❌ Out of Scope

  • Backend server / database infrastructure
  • User authentication / login system
  • Multi-player / team-based exercises
  • Real vulnerability exploitation tools
  • Network-level attack simulations
  • Custom lab authoring interface

Investigation Methodology

Each lab follows a structured, repeatable investigation loop modeled after professional penetration testing frameworks (OWASP Testing Guide v4, PTES):

Phase 1 — Observe

Interact with the simulated target application. Study login forms, API responses, URL parameters, HTTP headers, and UI behavior to build an initial threat hypothesis. This phase builds pattern recognition — the most critical skill for a security analyst.

Phase 2 — Probe

Actively test the hypothesis by manipulating inputs (credentials, URL parameters, form fields, request payloads). Observe how the target responds to crafted inputs. Identify error disclosure, parameter reflection, access control failures, or configuration weaknesses.

Phase 3 — Decide

Answer targeted assessment questions that validate understanding of the root cause, vulnerability classification (CWE), impact severity, and exploitation conditions. Wrong answers trigger specific feedback explaining the misconception.

Phase 4 — Mitigate

Select and justify the correct defensive control from multiple options. This reinforces the defender mindset: understanding not just what is broken, but how to fix it — input validation, parameterized queries, security headers, least-privilege access, etc.

⚠️ Sequential Progression Rule Labs are locked in strict sequential order. Lab N+1 becomes available only after Lab N is successfully completed. This ensures that foundational concepts (authentication, authorization) are mastered before advancing to more complex domains (injection, configuration, HTTP analysis).

03Lab Deep-Dive — Part I

Detailed investigation design for Labs 01, 02, and 03.

LAB 01 The Weak Front Door — Authentication Bypass

Beginner

Scenario: The learner encounters a simulated corporate login portal ("SecureVault") that leaks differential error messages. When an invalid username is submitted, the server responds "User not found"; when a valid username with wrong password is submitted, it responds "Invalid password" — enabling username enumeration.

Learning Objective: Understand how differential error responses create an information disclosure vulnerability (CWE-287). Recognize that consistent, generic error messages ("Invalid credentials") are the correct defensive pattern.

Investigation Steps:

  • Observe the login form and test with random credentials — note the specific error message returned.
  • Probe with different usernames — identify which usernames exist based on response variation.
  • Decide which vulnerability class this behavior represents (username enumeration via differential responses).
  • Final assessment: select the correct mitigation (generic error messages for all login failures).
Username Enumeration Error Disclosure Credential Stuffing Prevention OWASP A07:2021

LAB 02 Who Owns This Record? — IDOR / BOLA

Beginner

Scenario: A medical records portal ("MedFile") displays patient records via sequential URL parameter (?recordId=101). By manipulating this parameter, the learner discovers they can access other patients' records — a classic Insecure Direct Object Reference (IDOR) vulnerability.

Learning Objective: Understand that client-side URL parameters are user-controlled and must never be trusted as authorization checks. Learn that server-side ownership validation (comparing session identity against resource ownership) is mandatory.

Investigation Steps:

  • Observe the URL structure and note the sequential record ID parameter.
  • Probe by modifying the recordId parameter — access records belonging to other users.
  • Decide whether the application performs server-side authorization or relies on obscurity.
  • Final assessment: select the correct fix (server-side ownership validation per request).
IDOR BOLA Access Control Parameter Tampering OWASP A01:2021

LAB 03 Trust No Input — Reflected XSS

Intermediate

Scenario: A product search page reflects user input directly into the HTML response without sanitization. The learner tests a 7-vector input suite (normal text, empty string, boundary values, special characters, script tags, type confusion) and observes that script payloads are rendered as executable HTML.

Learning Objective: Understand reflected XSS attacks (CWE-79), input validation boundaries, output encoding requirements, and the defense-in-depth principle of Content Security Policy headers.

Reflected XSS Input Validation Output Encoding CSP Headers OWASP A03:2021

04Lab Deep-Dive — Part II

Detailed investigation design for Labs 04 and 05.

LAB 04 The Hardened Baseline — Security Misconfiguration

Intermediate

Scenario: The learner audits a simulated web server configuration manifest containing multiple security misconfigurations: debug mode enabled in production, default admin credentials, directory listing active, verbose error pages exposing stack traces, overly permissive CORS policy, and missing rate limiting.

Learning Objective: Develop the ability to systematically audit configuration files for security weaknesses. Understand the CIS Benchmark approach to baseline hardening and the principle of secure-by-default configurations.

Investigation Steps:

  • Observe the configuration manifest — scan each setting for deviations from security best practices.
  • Probe by flagging specific configuration lines as "insecure" or "acceptable" — the simulation provides per-line severity ratings.
  • Compare against a hardened baseline configuration to understand the correct values for each setting.
  • Decide which misconfiguration represents the highest severity risk and select the correct remediation priority.
Security Misconfiguration CIS Benchmarks Default Credentials Debug Mode CORS Policy OWASP A05:2021

LAB 05 The Wire Inspector — HTTP Security Analysis

Advanced

Scenario: The learner inspects raw HTTP request/response pairs captured from a simulated web application. They analyze response headers for missing security controls (Strict-Transport-Security, Content-Security-Policy, X-Frame-Options) and inspect Set-Cookie headers for missing security flags (Secure, HttpOnly, SameSite).

Learning Objective: Develop wire-level analysis skills — the ability to read raw HTTP traffic and identify security deficiencies. Understand the defense-in-depth role of transport security headers and cookie protection flags.

Investigation Steps:

  • Observe the raw HTTP response — identify present and missing security headers.
  • Probe the Set-Cookie header — check for Secure, HttpOnly, and SameSite flags.
  • Compare the insecure response against a hardened "safer response" showing all correct headers.
  • Multi-part final assessment covering HSTS enforcement, cookie flags, CSP directives, and clickjacking prevention.
HTTP Headers HSTS CSP Cookie Security X-Frame-Options OWASP A05:2021

State Management Architecture

The application uses a single React Context (AppProvider) with useCallback-memoized action dispatchers. All state mutations are immutable — each update produces a new state object, ensuring predictable rendering and clean undo semantics.

💾 Persistence Layer

State serialized to localStorage under key cyber-labs.v1. Auto-saved on every state change. Backward-compatible migration handles schema evolution.

🗂️ State-Based Routing

Custom router using discriminated union type (Route) instead of react-router. Zero external dependency. Compile-time route exhaustiveness checking via TypeScript.

🔄 Immutable Updates

All state mutations use spread-based immutable patterns. No direct mutation. Predictable rendering, easy debugging, and clean state rollback capability.

📊 Derived State

Computed values (totalScore, completedCount, skill radar data) derived via useMemo — recalculated only when underlying lab progress changes.

Security Boundary — Threat Model

The platform enforces a strict safe-simulation boundary to ensure educational exercises never pose real-world risk:

🚫 No Network Egress

Zero external HTTP requests. Every "server response" is a scripted, deterministic object defined in the lab data. No fetch(), XMLHttpRequest, or WebSocket connections to external hosts.

🔑 No Real Credentials

All usernames, passwords, session tokens, and API keys shown in labs are fictional examples. No real authentication systems are targeted or referenced.

⛔ No Code Execution

The XSS demonstration (Lab 03) uses a predefined, static payload rendered as HTML text in an isolated container. No user-typed input is ever evaluated as executable code.

🔒 Client-Side Only

The entire application runs in the browser sandbox. No server-side processing, no database queries, no file system access. The attack surface is limited to static HTML/CSS/JS assets.

✅ Safety Guarantee This platform is designed with the fundamental principle: "Teach attack techniques by building defender instinct — never by providing real attack tools." Every simulation is a faithful educational model, not a functional exploit kit. No real system has ever been targeted, and the architecture makes it impossible to do so.

Data Privacy

  • No personal data collection — The platform does not collect, store, or transmit any personal information.
  • No analytics / tracking — No Google Analytics, Mixpanel, Hotjar, or similar tracking is integrated.
  • No cookies — Only localStorage is used for progress persistence. No HTTP cookies are set.
  • No external API calls — Zero network requests to third-party services during application usage.

07Platform Features — Scoring, Progression & Gamification

Adaptive scoring engine, sequential lab progression, retake system, and achievement mechanics.

Adaptive Scoring Engine

Every lab uses a standardized base-100 scoring model designed to reward efficient investigation and penalize trial-and-error approaches:

// Scoring Formula
function computeScore(wrongAttempts, hintsUsed) {
  const base = 100;
  const penalty = (wrongAttempts × 3) + (hintsUsed × 5);
  return Math.max(60, base − penalty);
}

// Examples:
// Perfect run (0 wrong, 0 hints) → 100 points
// 2 wrong + 1 hint → 100 − 6 − 5 = 89 points
// 5 wrong + 3 hints → 100 − 15 − 15 = 70 points
// Floor: minimum score is always 60 (completion reward)

Sequential Lab Progression

Labs enforce strict sequential ordering to ensure foundational concepts are mastered before advancing:

  • Lab 01 (Authentication) → Starts unlocked for all users
  • Lab 02 (Authorization) → Unlocks only after Lab 01 completion
  • Lab 03 (Injection) → Unlocks only after Lab 02 completion
  • Lab 04 (Configuration) → Unlocks only after Lab 03 completion
  • Lab 05 (HTTP Security) → Unlocks only after Lab 04 completion

Retake System

Every completed lab has a "Retake Lab" button on the completion screen. This allows learners to replay the investigation with reset progress to improve their score. The retake resets score, attempts, hints, and step progress to zero while keeping other labs' progress intact.
